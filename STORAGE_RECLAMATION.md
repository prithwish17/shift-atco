# Supabase storage reclamation (free tier, 500 MB)

Goal: stay under the 500 MB free-tier database limit. This documents what the
`20260622100000_storage_reclamation.sql` migration does, the **one-time manual
step** you must run after it, and the diagnostics to confirm it worked.

## TL;DR of findings (measured 2026-06-22)

| Table | Rows | Action |
|---|---|---|
| `employee_schedules` | 84,676 | **All live** (Dec 2025–Jul 2026). Do NOT delete. Reclaim dead-tuple bloat with `VACUUM FULL`. |
| `api_call_logs` | 10,141 | Purge >30 days (daily). |
| `cron_job_queue` | 2,957 | **Had no cleanup** → purge finished jobs >3 days. |
| `notifications` | 2,035 | Purge >30 days. |
| `working_hours_cache` | 1,601 | Keep current + 1 prior month (it's already Redis-backed). |
| `email_logs` | 591 | Purge >30 days. |
| `*_archive` tables | empty | **Dropped** — they duplicated data in the same DB and saved nothing. |

The old `archive-old-logs` / `archive-old-api-logs` cron jobs only *moved* rows
into `*_archive` tables **inside the same database**, so they reclaimed 0 bytes.
They are now unscheduled and replaced by real deletes.

## Step 1 — Apply the migration

Either via the Supabase CLI:

```sh
cd shift-atco
supabase db push        # applies supabase/migrations/20260622100000_storage_reclamation.sql
```

…or paste the file's contents into **Supabase Dashboard → SQL Editor → Run**.

It: drops the archive tables/jobs, creates `purge_old_data()`, schedules a daily
purge (`30 3 * * *` = 09:00 IST) + a weekly light compaction, drops 7 redundant
indexes, and runs one purge immediately.

## Step 2 — One-time VACUUM FULL (this is what actually shrinks the DB)

`DELETE` only marks rows dead; the reported database size does not drop until a
`VACUUM FULL` rewrites the table. Run this **once**, ideally during low traffic
(each statement takes a brief exclusive lock on that table):

```sql
VACUUM (FULL, ANALYZE) public.employee_schedules;  -- biggest reclaim (re-sync bloat)
VACUUM (FULL, ANALYZE) public.api_call_logs;
VACUUM (FULL, ANALYZE) public.cron_job_queue;
VACUUM (FULL, ANALYZE) public.notifications;
VACUUM (FULL, ANALYZE) public.notification_queue;
VACUUM (FULL, ANALYZE) public.email_logs;
VACUUM (FULL, ANALYZE) public.working_hours_cache;
```

> ⚠️ `VACUUM FULL` needs free disk roughly equal to the table size to rewrite it.
> If you're already near the cap and a statement errors on space, run the smaller
> tables first (they free room), then retry `employee_schedules` last.

## Diagnostics — where the bytes actually are

Run before and after to measure the win:

```sql
-- Top 25 tables by total size, with dead-tuple bloat
SELECT relname AS table,
       pg_size_pretty(pg_total_relation_size(c.oid)) AS total,
       pg_size_pretty(pg_relation_size(c.oid))       AS data,
       pg_size_pretty(pg_indexes_size(c.oid))        AS indexes,
       s.n_live_tup AS live_rows, s.n_dead_tup AS dead_rows
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
LEFT JOIN pg_stat_user_tables s ON s.relid = c.oid
WHERE n.nspname = 'public' AND c.relkind = 'r'
ORDER BY pg_total_relation_size(c.oid) DESC
LIMIT 25;

SELECT pg_size_pretty(pg_database_size(current_database())) AS db_total;
```

Find any *other* unused indexes (drop large ones with `times_used = 0` that are
not backing a PK/unique constraint):

```sql
SELECT relname AS table, indexrelname AS index,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size, idx_scan AS times_used
FROM pg_stat_user_indexes
WHERE schemaname = 'public'
ORDER BY pg_relation_size(indexrelid) DESC;
```

## Verify the schedule is in place

```sql
SELECT jobname, schedule FROM cron.job
WHERE jobname IN ('purge-old-data','compact-log-tables');

-- confirm the old in-DB archive jobs are gone:
SELECT jobname FROM cron.job WHERE jobname LIKE 'archive-old%';   -- expect 0 rows

-- run the purge on demand any time:
SELECT public.purge_old_data();
-- or with custom windows, e.g. keep only 14 days of api logs:
SELECT public.purge_old_data(p_api_log_days => 14);
```

## Notes / decisions

- **Redis (`working_hours_cache`):** the table is already a *secondary* warm layer
  under the 20-min Upstash cache in `api/working-hours.ts`. A full Redis-only move
  buys little space for real refactor risk, and 6×/day refreshes would add load to
  the Upstash free tier. Instead we cap the table to the current + 1 prior month;
  anything older is regenerated by the RPC/Redis path on demand. `leave_balances_cache`
  is empty and left as-is.
- **`employee_schedules`:** nothing to archive (all rows are current/future roster
  data). The win there is purely the one-time `VACUUM FULL` reclaiming update bloat.
- Tune retention by editing the defaults in `purge_old_data(...)` and re-applying,
  or by passing named args to the scheduled call.
